How to tackle complex, long-running tasks with GitHub Copilot

Three practices that helped me escape the rework-and-regression loop and turn an unsuccessful 12-hour attempt into a reliable workflow for AI-assisted engineering.

Have you ever handed a complex task to GitHub Copilot, only to watch it stall out, get trapped in endless rework, or declare the job “complete” while introducing a wave of new bugs where fixing one bug breaks two more?

I hit that exact wall when I left Copilot working overnight on a complex performance optimization task. More than 12 hours later, I came back to a reassuring message: the task was complete.

There was just one problem. It was not. The implementation missed the performance target, introduced regressions, and every follow-up fix seemed to unravel something else.

That experience changed how I approach complex, long-running work with AI agents. For a small, self-contained edit, describing the desired outcome is usually enough. For work spanning architecture, experimentation, multi-file implementation, and validation, how we structure the workflow and allocate model capability across it matters just as much as the prompt itself.

I eventually resolved the performance issue. Looking back, three practices made the biggest difference:

  1. Get the design clear before implementation.
  2. Explore multiple approaches before committing.
  3. Invest model capability in those design decisions, then optimize implementation.

1. Get the design clear before implementation

My first attempt focused heavily on the outcome: improve performance while preserving existing behavior. That left too many interconnected decisions open during implementation. Small assumptions compounded, and the agent produced substantial work that still moved in the wrong direction.

What worked better was separating design from implementation. Before changing code, I worked with Copilot to clarify the architecture, component responsibilities, interactions, API contracts, invariants, and measurable success criteria.

Example prompt
Before making code changes, analyze the current architecture and propose a design for improving performance.

Identify component responsibilities, interactions, affected API contracts, behavior that must not change, likely bottlenecks, measurable success criteria, and a validation plan.

Call out assumptions, risks, and open questions. Do not implement anything yet.
Do not treat design as an implicit part of implementation. Make it a separate deliverable and review it before code changes begin.

2. Explore multiple approaches before committing

An agent can make the first plausible solution feel surprisingly complete. That momentum is useful, but it can lead us to commit too early. Instead of asking Copilot to find and implement one solution, I found it more effective to ask it to explore the solution space first.

Example prompt
Propose three viable approaches to this performance bottleneck. For each, include the expected impact, implementation complexity, compatibility risks, a quick experiment, and evidence that would cause us to reject it.

Do not implement the full solution yet. Recommend which approaches are worth prototyping in parallel.

Small prototypes helped answer specific questions before I invested in a production implementation. This changed the interaction from “implement this solution” to “help me explore the solution space.”

Use Copilot as a design exploration partner. Ask for alternatives, test the strongest assumptions, and let evidence guide the final choice.

3. Use stronger reasoning for design, then optimize for implementation

Practices 1 and 2 establish why upfront design and exploration are critical for a complex, long-running task. That leads directly to the next question: since design is where the highest-leverage decisions happen, how should I allocate AI capability across the workflow?

Instead of using a single model configuration from start to finish, I invest my strongest reasoning in the design decisions, capture those decisions in a concrete artifact, and then switch to a faster, more cost-efficient model for implementation.

How to allocate model capability across a complex, long-running task

Start with high capability and task fit during design, lock the decisions into an artifact, and then optimize for speed and cost during implementation.

Design & exploration: optimize for decision quality

For a complex, long-running task, the design phase carries the highest uncertainty and the highest downstream impact: a flawed architecture or direction will invalidate hours of downstream work. My default starting point for design is therefore a high-capability model with strong reasoning, and only then do I ask: among strong models, which one is particularly good at this task?

High capability is the baseline. Task fit determines which high-capability model I choose.

Across public benchmarks, complex software and knowledge work generally falls into four categories, each with different frontier leaders:

  • UI & frontend design: designing web interfaces, visual layouts, component hierarchies, and interactive user experiences. GPT-6 Astra and Claude Opus 5.5 rank highest here.
  • Backend & application coding: writing service and business logic in existing repositories, cross-file refactoring, fixing PR bugs, and migrating code across languages or frameworks. Claude Opus 5.5 and GPT-6.1 Sol perform best in this category.
  • Systems, CLI & DevOps: running shell scripts, configuring environments, troubleshooting in terminal or container workflows, and tuning system-level performance. Claude Opus 5.5 and GPT-6 Astra lead this category.
  • Writing, research & design docs: open-ended technical research, architecture trade-off analysis, design documents, and structured reports or presentations. Claude Opus 5.5 and Gemini 4 Argon lead this category.

Capture the design

Before switching models for implementation, lock the decisions from exploration into a concrete, reviewable artifact: a UI mockup, a design doc (design.md), an API contract, or an implementation plan.

Once the important decisions are captured in a concrete design artifact, the implementation problem becomes much more constrained.

Implementation & iteration: optimize for efficiency

With the design artifact locked, you can switch to a faster model with lower reasoning effort and lower cost. Because the implementation model no longer needs to re-architect the system, re-explore the solution space, re-decide API contracts, or re-interpret the UI direction, its job is simple:

Execute the reviewed design reliably and efficiently.

During implementation, you are running dozens of scoped coding, script-running, and test-fixing turns, so latency and cost become the primary optimization criteria:

  • Cost sweet spot (80%–95% lower cost): Stepping down from flagship Max (5) to GPT-6.1 Sol (Medium: $0.36/task) or GPT-6.1 Terra (High: $0.26/task) retains 80%–90% of flagship capability at 6%–10% of the cost of Claude Opus 5.5 (Max: $4.26/task).
  • Speed sweet spot (7–15s interactive turns): Medium (2) and High (3) keep coding and verification turns under 15 seconds, whereas Max (5) stretches single-turn wait times to 4.6–11.8 minutes and can even score slightly lower on reasoning benchmarks due to over-thinking.

Use your strongest reasoning where decisions are being made. Once those decisions are captured in a clear design, switch to a faster and more efficient model for execution.

Putting it all together

1. Clarify design
2. Explore options
3. High reasoning + fit
4. Capture the design
5. Optimize execution

For complex, long-running work, the best results came from making the design explicit, exploring alternatives before committing, investing high capability and task fit in those design decisions, capturing the decisions in a concrete artifact, and then switching to a faster, more cost-efficient model for implementation.

Final thoughts

The biggest lesson from my overnight experiment was not that GitHub Copilot could not handle a complex task. It was that I needed to work with it differently.

The goal is not to write one perfect prompt and walk away. It is to structure the work so that Copilot has the context, boundaries, and direction it needs to succeed.
