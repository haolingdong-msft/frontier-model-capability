How to tackle complex, long-running tasks with GitHub Copilot

A four-step workflow for turning open-ended, multi-hour engineering tasks into clear daytime designs and reliable overnight implementations.

Have you ever handed a complex task to GitHub Copilot, only to watch it stall out, get trapped in endless rework, or declare the job "complete" while introducing subtle regressions?

For a small, self-contained edit, describing the desired outcome in a single prompt is usually enough. But for genuinely hard, long-running tasks (such as performance enhancement with no accuracy downgrade, or changing deeply coupled domain logic with dozens of subtle edge cases), asking a single model to figure out the architecture, weigh trade-offs, edit dozens of files, and preserve every edge case inside one open-ended loop rarely works. Small early assumptions compound into hours of drifted code and wasted tokens.

The 4-step workflow for complex, long-running tasks

Instead of using a single model and a single open-ended prompt from start to finish, here is the repeatable four-step workflow you can follow on any complex engineering task:

Step 1 · Foundation
1. Understand the models Map each model's capability, cost, and speed across reasoning efforts to inform your choices in Steps 2 and 4.
Step 2 · Daytime Design
2. Choose the design model Shortlist top models by task type, then use Step 1's cost/speed curves when capability is close.
Step 3 · Daytime Design
3. Explore & write bounded specs Compare 2 to 3 viable approaches first, then freeze architecture, invariants, and bounded specs.
Step 4 · Overnight Code
4. Choose the implementation model Start a fresh session with a fast, lower-cost model at Medium effort (at most High) to execute specs in parallel.

Step 2: Choose the design model by task type

The design phase has fewer turns than implementation, but its decisions define the architecture for everything that follows. Because different models excel in different domains, check which models perform best on your specific task type:

1. UI Design / Mockup

Generating UI designs, interactive mockups, visual layouts, and web interface prototypes.

GPT-6 Astra and Claude Opus 5.5 perform best in this category.

2. App Coding

Writing application and domain logic in existing repositories, multi-file refactoring, CLI/systems workflows, and performance tuning.

Copilot Fusion Max (68.8%), Claude Opus 5.5 (xhigh: 62.4%), and Claude Sonnet 5.5 (xhigh: 58.8%) perform best in this category.

3. Data Analysis & Scientific Computing

Computational research workflows, quantitative data analysis, numerical simulation, and mathematical or engineering modeling in a terminal environment.

Copilot Fusion Max (66.0%), GPT-6 Astra (max: 64.6%), and Claude Opus 5.5 (xhigh: 54.3%) perform best in this category.

4. Agent Skills & Workflows

Authoring and executing structured Agent Skills (reusable packages of procedural domain knowledge, multi-step instructions, and verification scripts).

Claude Opus 5.5 (63.8%), Claude Sonnet 5.5 (xhigh: 60.0%), and GPT-6 Astra (xhigh: 55.0%) perform best in this category.

Step 3: Explore approaches and write bounded design specs

Once you have selected a strong reasoning model for design, resist the urge to ask it to write production code right away. Because different approaches correspond to different target architectures, use your daytime interactive session to do two things in order: first explore multiple viable approaches and their trade-offs, and then define the architecture, invariants, and bounded specification for each selected approach.

3.1 Explore multiple viable approaches and trade-offs first

An agent can make the first plausible idea look deceptively complete, tempting us to commit too early or bundle several unverified ideas into one sprawling branch. Before locking in an architecture or writing code, ask your design model to analyze the root causes, propose 2 to 3 distinct approaches, and compare their trade-offs.

Prompt template: Explore root causes and candidate approaches
Before making code changes, analyze the problem and root causes for this task, then propose 2 to 3 viable approaches.

For each approach, compare:
1. High-level concept and expected impact on the goal.
2. Architectural trade-offs and implementation complexity.
3. Compatibility or quality risks and what evidence would cause us to reject it.

Write the comparison to docs/approaches.md. Do not implement anything yet.

3.2 Define the architecture, invariants, and bounded spec for each chosen approach

Because each candidate approach shapes component boundaries and data flow differently, define the detailed architecture only after choosing which approach(es) to pursue. For each selected approach, work with your design model to write a self-contained, bounded spec covering its component responsibilities, contracts, edge-case invariants that must not regress, and verification criteria.

Prompt template: Define architecture, invariants, and bounded specs
For each selected approach in docs/approaches.md, write a separate, self-contained design and implementation spec (plan-1.md, plan-2.md, etc.) specifying:
1. Target architecture: component responsibilities, interactions, and input/output contracts.
2. Exact scope: allowed files to modify and files that are off-limits.
3. Non-negotiable invariants: existing behavior, output quality requirements, and edge cases that must not regress.
4. Verification commands and measurable acceptance criteria.
Write your chosen approach and implementation plan into Markdown files (such as design.md or plan-1.md) before writing code, so the coding agent in Step 4 can follow a clear spec instead of guessing the architecture.

Step 4: Choose a faster, lower-cost model for implementation

Once your implementation plan is written down in Step 3, the hard design decisions are already made. Coding is mostly following the plan: editing files, running tests, and fixing errors across many turns. At this stage, speed and cost matter more than maximum reasoning:

1. Pick a faster, lower-cost model

In the Step 1 charts, models like GPT-6.1 Sol ($0.62–$0.80/task) and Claude Sonnet 5.5 ($0.85–$1.36/task) keep strong coding accuracy while cutting cost by 75% to 85% and finishing in 8 to 10 minutes.

2. Medium effort is enough (at most High)

Since the plan already specifies which files to edit and how to verify the result, Medium effort is usually enough (at most High)—saving the extra time and cost of xHigh or Max.

3. Open a new session to implement

Switching models back and forth in the same chat breaks Copilot's prompt caching. Finish your design in one session, save the plan to a file, and start a new session to write the code.

Once your plan is written down, start a new session with a fast, lower-cost model (such as GPT-6.1 Sol or Claude Sonnet 5.5) at Medium effort (at most High) to implement and test the code.

A real example: Enhancing skill performance without losing output quality

To see how all four steps come together in practice, here is a real task: enhancing the performance of an agent skill (cutting runtime from 22 minutes to under 5 minutes) without downgrading output quality across 12 benchmark cases.

Before · Unstructured One-Shot Attempt

When I initially gave GPT-6 Astra one open-ended overnight prompt to optimize the skill, it spent 12 hours and 160.5M tokens (1,583 calls), hit the < 5 min target on 0/12 cases, degraded output quality on 11/12 cases by taking shortcuts, and cost me 2.5 hours the next morning just to audit and git revert the branch.

After · Applying the 4-Step Workflow
  • Steps 1 & 2 (Choose the design model & effort): Because diagnosing and redesigning the skill combines App Coding and Data Analysis & Scientific Computing (profiling phase latencies and token distributions), I selected GPT-6 Astra at High effort for the afternoon design session.
  • Step 3 (Explore approaches & write bounded specs): In a 2.5-hour daytime design session (35.7M tokens), we first explored the runtime bottlenecks (docs/approaches.md) and then defined the target architecture, output-quality invariants, and three bounded specs to build in parallel: Plan A (deterministic setup), Plan B (parallel compiler passes), and Plan C (compacting model input from 1.6 MB to 300 KB with a deterministic report builder).
  • Step 4 (Choose the implementation model & effort): Before logging off, I opened three isolated Git worktrees and handed Plan A, Plan B, and Plan C to GPT-5.6 Sol at Medium/High effort to implement and verify against the 12-case benchmark suite overnight.

Applying this four-step workflow reduced both Copilot token cost and compute usage, while delivering the target speedup with zero output regressions:

2-day Copilot token usage (449.3M → 105.0M)
-76% Compute
Overnight session AIU cost (26,331 → 6,279 AIU)

Skill runtime (~80% faster, 12/12 passing)

Putting the workflow into practice

1. Understand the models
2. Choose the design model
3. Explore & write bounded specs
4. Choose the implementation model

For any complex, long-running engineering task, resist the temptation to hand the entire problem to a single model in one prompt. Understand how the Claude and GPT families trade off peak resolution against per-task cost (Step 1), pick a high-reasoning model for daytime design (Step 2), explore options and lock down bounded design specs (Step 3), and then switch to cost-efficient GPT models to implement those specs in parallel worktrees overnight (Step 4).

The goal is not to write one perfect prompt and walk away. It is to structure the work so that Copilot has the context, boundaries, and direction it needs to succeed.
