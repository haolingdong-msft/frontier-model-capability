How to tackle complex, long-running tasks with GitHub Copilot

A simple four-step workflow: use a strong reasoning model to design a clear plan during the day, then switch to a faster, cheaper model to write the code overnight.

Have you ever given GitHub Copilot a big, multi-hour task—only to come back later and find it stuck in a loop, burning through tokens, or claiming “done!” while quietly breaking existing behavior?

For small, self-contained edits, a single prompt works great. For hard tasks—like making a system 5× faster without hurting quality, or changing core logic with tricky edge cases—asking one model to figure out the design, weigh trade-offs, edit dozens of files, and test everything in a single open-ended prompt rarely works. One bad early guess snowballs into hours of wasted work.

The 4-step workflow

Instead of pasting one giant prompt and hoping for the best, split daytime design from overnight coding in four steps:

Step 1 · Foundation
1. Understand the models See how Copilot models trade off accuracy, cost, and speed as you raise thinking effort.
Step 2 · Daytime Design
2. Pick a design model Choose a top model for your task type. If two models are close, pick the faster or cheaper one.
Step 3 · Daytime Design
3. Write a clear plan Compare 2–3 options first, then write down the exact files, guardrails, and tests in a plan.md file.
Step 4 · Overnight Code
4. Code with a fast model Start a fresh session with a faster, cheaper model at Medium effort (at most High) to build the plan.

Two practical takeaways jump out from these curves:

Pattern 1 · Model Tiers

Heavyweights vs. fast value models

  • Heavyweights (Copilot Fusion Max, Claude Opus 5.5, Claude Sonnet 5.5 at high effort, Claude Fable 5.2) solve the hardest problems (57%–68.5%), but cost $4–$33/task and run longer. Save them for design.
  • Fast value models (GPT-6.1 Sol, Copilot Fusion High, GPT-6.1 Terra) still solve 38%–54.5% of tasks for just $0.33–$1.77 in 6–15 minutes—ideal for coding.
  • Lightweight models (GPT-6 Luna) cost pennies, but struggle on complex multi-step tasks (<15%).
Pattern 2 · Thinking Effort

Turn up effort to High or xHigh—rarely Max

  • Raising effort from Low (1) to High (3) or xHigh (4) gives a big accuracy jump on most models (for example, Claude Opus 5.5 climbs from 36.4% to 62.1%, and Claude Sonnet 5.5 jumps from 21.8% to 55.5%).
  • Going all the way to Max (5) rarely pays off: cost and wait time roughly double, while accuracy plateaus or even dips slightly (Opus 5.5 and Fable 5.2).
Use Step 1 as your reference map: heavyweight models give you peak reasoning for hard design choices, fast value models give you the best speed and cost for coding, and Max effort is rarely worth double the wait and bill.

Step 2: Pick a strong design model for your task type

Step 1 showed how models behave on terminal coding tasks, but no single model wins every kind of work—for example, GPT-6 Astra sits mid-pack on CLI tasks, yet ranks #1 on UI design and top-3 on scientific computing. Because your daytime design chat is short and shapes everything that follows, start by picking a top model for your specific task:

1. UI Design / Mockup

Designing web pages, visual layouts, and interactive UI prototypes.

Top picks: GPT-6 Astra (1,339 Elo) and Claude Opus 5.5 (1,325 Elo).

2. Agentic Coding

Writing application logic, refactoring across files, CLI workflows, and performance tuning.

Top picks: Copilot Fusion (Max: 68.5%, High: 54.5%), Claude Opus 5.5 (xHigh: 62.1%), Claude Sonnet 5.5 (Max: 62.1%), and Claude Fable 5.2 (57.3%).

3. Data Analysis & Scientific Computing

Analyzing datasets, profiling bottlenecks, and running math, science, or engineering scripts.

Top picks: Claude Fable 5.2 (High: 74.3%), Copilot Fusion (Max: 68.6%), and GPT-6 Astra (Max: 62.0%)—or GPT-6.1 Sol (54.6% at $2.56) on a budget.

4. Agent Skills & Workflows

Building and running reusable Copilot skills, custom instructions, and multi-step workflows.

Top picks: Claude Opus 5.5 (Medium: 63.8%), Claude Sonnet 5.5 (xHigh: 60.0%), and GPT-6 Astra (xHigh: 55.0%).

Step 3: Explore options first, then write a clear plan

Once you have picked a strong design model, don’t ask it to write code right away. When Copilot jumps straight into coding, it locks onto the first idea it thinks of—even if that approach is slow, over-complicated, or breaks subtle edge cases. Instead, spend your daytime chat doing two quick steps before any code is touched:

3.1 Ask for 2–3 options before picking a direction

Ask Copilot to find the root cause of the problem and propose 2 to 3 different ways to solve it, along with the pros, cons, and risks of each. That lets you choose the right direction in minutes instead of discovering a dead end hours later.

Prompt template: Compare 2–3 approaches first
Before changing any code, analyze the root causes of this problem and propose 2 to 3 different approaches to solve it.

For each approach, explain:
1. How it works and the expected improvement.
2. Trade-offs and how complex it is to build.
3. What existing behavior or quality could break.

Save the comparison to docs/approaches.md. Do not write any code yet.

3.2 Turn your chosen option into a clear plan file

Once you pick which approach (or approaches) to try, ask your design model to write a standalone plan file (plan-1.md, plan-2.md, etc.). Think of this file as the handoff checklist for your coding agent—it spells out what to build, which files it may touch, what must not break, and how to test the result.

Prompt template: Write a clear implementation plan
For each selected approach in docs/approaches.md, write a standalone implementation plan (plan-1.md, plan-2.md, etc.) that clearly lists:
1. Design: what each part does and its inputs/outputs.
2. Scope: which files to edit, and which files are off-limits.
3. Guardrails: existing behavior, quality bars, and edge cases that must not break.
4. Verification: exact test commands to run and what "passing" looks like.
Save your chosen approach and implementation checklist into Markdown files (such as design.md or plan-1.md) before writing code. A written plan gives the coding agent in Step 4 clear instructions instead of forcing it to guess.

Step 4: Switch to a faster, cheaper model to write the code

Once plan-1.md is written, the hard design decisions are already made. Writing the code is mostly execution: editing files, running tests, and fixing errors over many turns. At this stage, speed and cost matter much more than maximum reasoning:

1. Pick a fast, low-cost model

Models in the upper-left of Step 1—like GPT-6.1 Sol ($0.63–$0.86/task), GPT-6.1 Terra ($0.33–$0.48/task), or Copilot Fusion (High) ($1.77/task)—cut cost by 75% to 90% vs. heavyweight xHigh/Max models and finish in 6 to 15 minutes.

2. Medium effort is enough (at most High)

Because your plan file already specifies which files to edit and how to verify them, Medium effort is usually enough (at most High)—saving the extra wait time and cost of xHigh or Max.

3. Start a fresh chat session

Switching models mid-conversation breaks Copilot’s prompt caching. Finish your design in one chat, save the plan to a file, and open a new session (or separate Git worktrees) to write the code.

Start a new session with a fast, lower-cost model (such as GPT-6.1 Sol, GPT-6.1 Terra, or Claude Sonnet 5.5 at Medium/High effort, or Copilot Fusion at High) and hand it your saved plan.md to build and test.

A real example: Speeding up a 22-minute skill without losing quality

Here is how these four steps worked on a real task: speeding up an agent skill from 22 minutes to under 5 minutes, while keeping report quality intact across all 12 benchmark cases.

Before · One Open-Ended Prompt Overnight

At first, I gave GPT-6 Astra a single open-ended prompt and let it run overnight:

"Help me improve the performance to meet 5 mins target, at the same time avoid reports quality regression by running benchmark."

What happened: It ran for 12 hours and burned 160.5M tokens (1,583 calls)—yet 0 out of 12 cases hit the 5-minute target, and 0 out of 12 reports met our quality bar because the agent cut corners to save time. I spent 2.5 hours the next morning reviewing the mess only to git revert the entire branch.

After · Following the 4-Step Workflow
  • Steps 1 & 2 (Pick a strong design model): Finding why the skill was slow needed both Agentic Coding and Data Analysis (profiling latency and token usage), so I picked GPT-6 Astra at High effort for an afternoon design chat.
  • Step 3 (Explore options & write clear plans): In 2.5 hours (35.7M tokens), we identified the real bottlenecks (docs/approaches.md), wrote strict quality guardrails so reports couldn’t be watered down, and split the work into three standalone plans: Plan A (replace slow LLM setup with a script), Plan B (run compiler checks in parallel), and Plan C (shrink model input from 1.6 MB to 300 KB and generate the final report with a script).
  • Step 4 (Code with a fast model in parallel): Before logging off, I opened three clean Git worktrees with fresh sessions and handed Plan A, Plan B, and Plan C to GPT-5.6 Sol (the predecessor to GPT-6.1 Sol) at Medium/High effort to build and run all 12 benchmark tests overnight.

Splitting daytime design from overnight coding cut both token usage and compute cost by over 75%, while hitting the speed goal with zero quality regressions:

Putting it into practice

1. Understand the models
2. Pick a design model
3. Write a clear plan
4. Code with a fast model

Next time you face a complex, multi-hour task, resist the urge to paste one big prompt and walk away. Check how models trade off accuracy, cost, and speed (Step 1), use a top model for your task type during the day (Step 2) to compare options and write a clear plan.md (Step 3), and then start a fresh session with a fast, cost-efficient model at Medium effort to build and test it overnight (Step 4).

The secret isn’t writing one magic prompt and walking away—it’s giving Copilot clear plans, clear guardrails, and the right model for each phase of the work.
