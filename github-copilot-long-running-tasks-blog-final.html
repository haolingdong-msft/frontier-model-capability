How to tackle complex, long-running tasks with GitHub Copilot

Three practices that helped me turn an unsuccessful 12-hour attempt into a more reliable workflow for AI-assisted engineering.

I once left GitHub Copilot working overnight on a complex performance optimization task. More than 12 hours later, I came back to a reassuring message: the task was complete.

There was just one problem. It was not.

The implementation missed the performance target and introduced regressions. That experience changed how I approach complex, long-running work with AI agents. For a focused coding task, describing the desired change may be enough. For work spanning architecture, experimentation, implementation, and validation, how we structure the journey matters just as much as the destination.

I eventually resolved the performance issue in the TypeSpec assessment skill. Looking back, three practices made the biggest difference:

  1. Get the design clear before implementation.
  2. Explore multiple approaches before committing.
  3. Choose the right model by balancing task type, latency, and cost.

1. Get the design clear before implementation

My first attempt focused heavily on the outcome: improve performance while preserving existing behavior. That left too many interconnected decisions open during implementation. Small assumptions compounded, and the agent produced substantial work that still moved in the wrong direction.

What worked better was separating design from implementation. Before changing code, I worked with Copilot to clarify the architecture, component responsibilities, interactions, API contracts, invariants, and measurable success criteria.

Example prompt
Before making code changes, analyze the current architecture and propose a design for improving performance.

Identify component responsibilities, interactions, affected API contracts, behavior that must not change, likely bottlenecks, measurable success criteria, and a validation plan.

Call out assumptions, risks, and open questions. Do not implement anything yet.
Do not treat design as an implicit part of implementation. Make it a separate deliverable and review it before code changes begin.

2. Explore multiple approaches before committing

An agent can make the first plausible solution feel surprisingly complete. That momentum is useful, but it can lead us to commit too early. Instead of asking Copilot to find and implement one solution, I found it more effective to ask it to explore the solution space first.

Example prompt
Propose three viable approaches to this performance bottleneck. For each, include the expected impact, implementation complexity, compatibility risks, a quick experiment, and evidence that would cause us to reject it.

Do not implement the full solution yet. Recommend which approaches are worth prototyping in parallel.

Small prototypes helped answer specific questions before I invested in a production implementation. This changed the interaction from “implement this solution” to “help me explore the solution space.”

Use Copilot as a design exploration partner. Ask for alternatives, test the strongest assumptions, and let evidence guide the final choice.

3. Choose models in layers: capability, fit, then efficiency

When choosing a model, I used to frame the decision as a choice between the “smartest” model and a model that was particularly good at a certain task. In practice, those ideas are not contradictory—they belong at different layers of the decision. And the first layer is not “always pick the strongest model,” but setting the right capability bar for the current step.

Capability bar first. Task fit second. Efficiency third.

Task fit cannot compensate for insufficient reasoning when a problem is ambiguous or cross-cutting. Start by asking which models clear the capability bar for the problem, refine by task fit among the models that clear it, and then optimize for cost and latency.

A layered model-selection framework

Move from left to right. Each step narrows the candidate models.

1. Set the capability bar for the problem

For complex architecture, ambiguous UX flows, or high-impact decisions, the capability bar is high. A model needs enough reasoning ability, reliability, and instruction-following strength to handle the uncertainty before specialization, price, or speed becomes useful.

This does not mean design always requires an expensive model—it means design usually carries higher uncertainty, which raises the capability bar. Once those decisions are captured in a mockup or reviewed design doc, the problem is constrained, the capability bar drops, and more models can clear it.

The best model changes as the task becomes better defined and the capability bar shifts.

2. Use task-specific strengths to refine the choice

Once multiple models are capable enough, task fit becomes meaningful. Some models may be especially effective at visual and UI work, others at coding, and others at organizing and polishing documentation.

The best model can therefore change several times within the same project.

WorkflowHigh-uncertainty workWell-defined execution
UIUse a strong model with good visual and UI capabilities to explore the experience, compare directions, and create a mockup.Once the mockup and component behavior are clear, use a faster, lower-cost coding model to implement and iterate.
Backend or serviceUse a strong reasoning model to design the architecture, APIs, data flow, failure cases, and compatibility boundaries.After capturing those decisions in a reviewed design document, use a more efficient coding model for scoped implementation tasks.
Design documentationIf the technical substance is unresolved, use a strong reasoning model to work through decisions, tradeoffs, and the outline.Once the substance is clear, use a model that is especially good at writing, structure, clarity, and tone.
Routine codingA separate high-cost design step may not be necessary when the change is already clear and low risk.Use a fast, lower-cost model for repetitive edits, tests, and small fixes.
Use capability to handle complexity, specialization to match the work, and cost and latency to optimize execution.

3. Optimize cost and latency after the quality bar is met

Cost and latency matter, but they should not be the first filter for difficult work. First identify the models that can reliably meet the quality bar. Then compare efficiency among those candidates.

This avoids two common mistakes:

  • Choosing a cheap model that cannot handle the problem reliably.
  • Using the most expensive model for every step, even after the task has become predictable and constrained.

High-impact decision: I am willing to pay more and wait longer when deeper reasoning can change the outcome.

High-frequency execution: Once the direction is clear, I optimize for faster responses and lower cost.

Selection rule: start with overall capability for difficult work, refine by task-specific fit, then choose the lowest-cost and lowest-latency option that reliably meets the quality bar.

The goal is not to find one best model for the entire project. It is to use the right level and type of intelligence for each part of the workflow.

For complex, long-running work, the best results came from making the design explicit, exploring alternatives before committing, and matching the model configuration to the task. The agent can still do substantial work, but clear checkpoints let a human verify direction before the cost of being wrong grows.

Final thoughts

The biggest lesson from my overnight experiment was not that GitHub Copilot could not handle a complex task. It was that I needed to work with it differently.

The goal is not to write one perfect prompt and walk away. It is to structure the work so that Copilot has the context, boundaries, and direction it needs to succeed.
